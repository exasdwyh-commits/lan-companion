# 读书与唱歌：整体规划与优化建议

更新：2026-10-31。基于当前代码实测，不是设想。

范围：`MALFOY-ENGINE/lib/{companion-media,narration,voice-script,book-analysis,cover-jobs}.js`、
`MALFOY-ENGINE/web/live2d/{companion-panel,companion-playback}.js`、`scripts/sing_cover_file.sh` 及其 Python 工具。

---

## 一、现状

两条链路共用一部分底座，但**各自长出了一套状态与存储**。

```
渲染层
  companion-playback.js  Player（38 行）
    ├─ 真正持有 <audio>，按 token 仲裁，有 generation 防竞态
    └─ 只知道「放什么」，不知道「为什么放」

  companion-panel.js     UI 三个 tab：chat / singing / reading

主进程
  companion-media.js（427 行）—— 一个闭包同时管五件事
    ├─ 书：book / chapters / cast / analysis（normalizeBook 兼容 v1/v2）
    ├─ 朗读状态机：state{kind,status,time} + token
    ├─ 预取缓存：prefetch（已完成）+ inflight（进行中）
    ├─ 曲库 A：读 companion-content/songs.json（pack 里的 2 首原曲）
    └─ 播放入口：playSong(id) / playAudio(p)

  cover-jobs.js（66 行）
    ├─ 翻唱作业：job{id,status,error} —— **内存变量**
    ├─ 曲库 B：读 <data>/covers/library.json（翻唱成品）
    └─ spawn 子进程跑 scripts/sing_cover_file.sh

数据落盘
  <data>/reading.json          书 + 章节 + 角色表
  <data>/reading-progress.json 只存 {bookId, index}
  <data>/covers/<uuid>/        原曲 + cover.m4a + 中间产物
  <data>/covers/library.json   翻唱成品索引
  companion-content/songs.json 原曲索引（只读，随包发布）
```

## 二、问题清单

按「用户能不能感知到」排序，不按代码美观度。

### P0-1 读书音轨完全不落盘，重启/回退必然重合成

**证据**：`companion-media.js` 里没有任何 `Buffer.from(sp.audio)` 落盘或 mp3 写文件；
音轨只经 `send({action:'load', audio: sp.audio})` 一次性传给渲染层。

**后果**：`reading-progress.json` 记住了读到第 N 段，但第 N 段的音轨早已随进程消失。
重启后点「继续」要重新合成；往回翻一段也要重新合成。
按实测 TTS ≈1.06 秒/次，一本 300 段的书从头听一遍就是 300 次合成；
多角色段（一次 4~6 句）还要乘上句数。

**这是当前最影响体验的一条**，且成本最低 —— 音轨本来就已经生成了，只是没存。

### P0-2 翻唱作业状态只在内存，重启后可能留下孤儿进程

**证据**：`cover-jobs.js:9` `let job = null`，`rows` 才是从 `library.json` 读的（只含已完成的）。
`cancel()` 靠 `child.pid` 发信号，而 `child` 也是内存变量。

**后果**：翻唱跑到一半 app 重启 → 状态全丢，但 `sing_cover_file.sh` 子进程可能还在跑（或已被系统回收）。
用户看到的是「什么都没发生」，实际磁盘上可能有半套中间产物。下次再点开始会从头来。

**注意**：管线本身是幂等的（每步检查产物是否存在），所以**能力是有的，缺的只是状态对账**。

### P0-3 两套曲库、两个数据源、两条播放路径

**证据**：
- 原曲：`companion-media.js:111` 读 `songs.json` → `playSong()`
- 翻唱：`cover-jobs.js:8` 读 `library.json` → 渲染层 `cover({action:'play'})`

UI 的 singing tab 同时渲染 `songs` 和 `cover-songs` 两个列表，来自两次不同的 `publish`。

**后果**：用户心智里「歌」是一个东西，代码里是两个。加新歌要改两处；
「正在播放哪一首」要在两套状态里各自维护。

### P1-1 `companion-media.js` 职责过载

427 行一个闭包，同时是：书的仓库、朗读状态机、预取调度器、曲库、播放门面。
改读书要碰它，改唱歌也要碰它 —— 这是最容易互相踩踏的地方（本轮修预取 bug 时就踩到）。

### P1-2 「当前在播什么」有三个真相源

- `companion-media.state`（主进程认为的）
- `Player.current`（渲染层实际的）
- `cover.job.status`（翻唱作业的）

三者靠 `token` / `generation` 手工对齐。读书侧已经修过一次竞态（预取 in-flight 重复合成），
唱歌侧目前没有对应的防护。

### P1-3 模型调用没有统一调度

- 读书：TTS 受控并发 3（`voice-script.js` 的 `mapLimit`）
- 翻唱：整条 shell 管线，自己串行
- 两者互不知情：一边在读长段落，一边在做翻唱，会同时压本地模型服务

没有优先级（用户主动点的应该优先于后台预取），没有统一的重试与降级记录。

### P2 体验层

- 翻唱只有状态字符串（`separating` / `converting`…），没有百分比或剩余时间；长歌十几分钟里只有一句话。
- 读书预取只挡「下一段」，一段内 6 句对白仍是串行等待（并发已加，但段与段之间仍有空隙）。
- reading tab 信息密度高（模式 / 角色表 / 章节 / 进度 / 分析状态），缺一句「现在是什么情况」。

## 三、目标架构

原则：**能共用的共用，该分开的分开**。不为架构而架构。

```
                  ┌──────────────────────────────┐
                  │  media-session（新，~80 行）  │
                  │  唯一的「当前在播什么」        │
                  │  acquire(kind, token) / release│
                  └──────────┬───────────────────┘
                             │
      ┌──────────────────────┼──────────────────────┐
      │                      │                      │
┌─────▼──────┐        ┌──────▼──────┐        ┌──────▼──────┐
│ book-store │        │reading-sess │        │song-library │
│ 书/章节/角色│        │ 朗读状态+预取 │        │ 原曲+翻唱统一 │
│ (~150 行)  │        │ (~180 行)    │        │ (~120 行)    │
└────────────┘        └─────────────┘        └─────────────┘
      │                      │                      │
      └──────────────────────┼──────────────────────┘
                             │
                  ┌──────────▼───────────┐
                  │  audio-cache（新）    │
                  │  音轨落盘 + LRU      │
                  └──────────────────────┘
                             │
                  ┌──────────▼───────────┐
                  │  model-queue（新）    │
                  │  TTS / SVC 统一排队   │
                  └──────────────────────┘
```

拆成三个 store 不是为了好看，是因为它们**变化的原因不同**：
书的结构变了不该影响播放，翻唱加了字段不该碰朗读逻辑。

`audio-cache` 和 `model-queue` 是两条链路真正共用的东西，所以单独抽出来。

## 四、分阶段实施

每阶段独立可交付、可回退。**先做 P0，做完就能明显感觉到差别。**

### 阶段一：读书音轨落盘（P0-1）✅ 已落地 2026-10-31

> 实现：新增 `MALFOY-ENGINE/lib/audio-cache.js`（约 110 行），`companion-media.js` 的 `render()`
> 增加 `index` 参数并在前后各接一次缓存。实测：首次朗读 2 次 TTS（当前段 + 预取下一段），
> **重启后重读同一段新增调用 0 次**；改角色音色（`bumpRev`）后缓存正确失效。
> 测试 181 → 183。

- 新增 `lib/audio-cache.js`：`get(key)` / `put(key, buffer)` / 容量上限 + LRU 淘汰。
  落盘路径 `<data>/audio-cache/<sha1(cacheKey)>.mp3`，缓存键沿用现有的
  `${bookId}:${rev}:${index}:${profile}`（rev 变了旧音轨自然失效，不需要额外清理逻辑）。
- `companion-media.js` 的 `render()` 前后各接一次：先查缓存，命中直接返回；
  未命中合成后写入。`prefetch` 也走同一条路。
- 容量：默认 200MB，超出按最近最少使用淘汰；`reading.json` 换书时不清缓存（书可回退）。
- **验收**：读到第 10 段 → 退出 → 重进 → 点继续，第 10 段应**秒开**（无 TTS 调用）。
  用真实 TTS 计数验证，不看日志猜。

**风险**：`rev` 语义要守死 —— 改角色表/切模式会 `bumpRev()`，旧缓存自动不命中，
否则会出现「换了音色还在放旧声音」。

### 阶段二：翻唱作业状态落盘 + 启动对账（P0-2）

- `job` 落盘到 `<data>/covers/<id>/job.json`（status / pid / startedAt / error）。
- 启动时对账：有 `job.json` 且 `pid` 仍存活 → 标为 `running` 继续跟踪；
  pid 已死 → 按产物判断，有 `cover.m4a` 标 `done`，否则标 `interrupted` 并提示可重试。
- **验收**：翻唱跑到一半 kill app，重开后状态应是 `interrupted`（不是「什么都没发生」），
  且点重试能复用已有中间产物（管线本来就幂等）。

### 阶段三：统一曲库（P0-3）✅ 已落地 2026-10-31

> 实现：新增 `MALFOY-ENGINE/lib/song-library.js`，把 `songs.json`（随包原曲）与
> `covers/library.json`（用户翻唱）合成一个列表，提供 `search()`；`playSong` 与原翻唱播放
> 合流到一条路径；面板两个列表合成一个 `#song-list`，加搜索框（200ms 防抖）。
> 顺带把「历史念词实验」用 `experimental` 标记折进 details，不再混在正常曲库里。
> 测试 183 → 188。

- `song-library.js` 合并两个数据源，对外一个 `songs[]`，每项带 `source: 'pack' | 'cover'`。
- `playSong` 与 `cover({action:'play'})` 合成一条播放路径，都走 `media-session`。
- UI 的 singing tab 只渲染一个列表，用来源标签区分（原曲 / 她的翻唱）。
- **验收**：原曲与翻唱能连续切换播放不叠播；列表只有一个数据源。

### 阶段四：拆分 companion-media（P1-1）

- 按上面的目标架构拆成 `book-store` / `reading-session` / `song-library`，
  `companion-media.js` 退化成薄门面（保持现有 `command()` 契约不变，外部零改动）。
- **验收**：现有 181 项测试全绿不改断言；`main.js` 只改 require 一行。

### 阶段五：统一模型调度（P1-3）

- `model-queue.js`：TTS 与 SVC 共用一个队列，分优先级
  （用户主动请求 > 预取 > 后台分析），记录每次调用的引擎、耗时、失败原因。
- **验收**：读书预取与翻唱同时进行时，用户点「读这段」的请求不被预取堵住。

### 阶段六：体验（P2）

- 翻唱进度：`sing_cover_file.sh` 每步写一行状态到 `progress.json`，UI 显示「第 3/5 步 · 转换音色」。
### 已修：唱歌链路的依赖健壮性（2026-10-31）

用户报「Qwen 女主参考音色暂时不可用」。它不属于任何一个阶段，而是暴露了本规划的
一个盲区：**我们把「读书和唱歌」当两个功能设计，却没把「它们共用同一个外部 TTS 服务」
当成架构问题**。该服务不在，两个功能以不同方式坏掉 —— 读书静默降级、翻唱直接报错。

三处改动：

- **翻唱参考改读定稿资产**，不再每次现场合成。音色是产品决定，不该是运行时产物。
- **TTS 服务由 App 保活**（`scripts/ensure-tts-server.sh`，启动时 + 失败时各调一次）。
  本机 launchd 拒绝新 LaunchAgents，所以只能「谁依赖谁负责」。
- **服务端推理加串行锁**，客户端合成并发 3 → 1。加锁后并发是负收益（7.8s vs 6s）。

这条给阶段五提了个新要求：统一模型调度不只要管「谁优先」，还要管**服务本身的存活**，
并且要区分「可以降级的调用」（读书）与「不能降级的调用」（翻唱参考音色）。
详见 [根因与修复](updates/2026-10-31-DW-05-tts-voice-asset.md)。

## 五、明确不做

- **不重写 Player**。`companion-playback.js` 38 行，职责干净（持有 audio + token 仲裁），
  问题不在这里，改它只会引入新竞态。
- **不把读书音轨塞进 `reading.json`**。base64 会让书文件膨胀几个数量级，
  且每次保存都要重写整个文件。落盘到独立目录、用键寻址才对。
- **不做跨设备同步 / 云端缓存**。当前是单机产品，没有这个需求。
- **不给翻唱加断点续传协议**。管线已经幂等，重启后重跑同一条命令就能续上，
  需要补的是**状态可见**，不是续传机制。
- **不合并 TTS 与 Seed-VC 的进程模型**。一个是常驻 HTTP 服务，一个是批处理子进程，
  硬合并会牺牲各自的可替换性。共用的是**调度**，不是运行时。

---

## 六、建议顺序

先做**阶段一**：投入最小（新增一个 80 行的缓存模块 + 两处接线），
但直接消灭「每次重听都要等」这个最难受的点。

再评估是否继续 —— 阶段二、三解决的是「状态不可信」和「数据源分裂」，
价值真实但用户感知弱于阶段一。阶段四、五属于架构健康，适合在功能稳定后再动。

## 七、娱乐系统扩展（2026-10-31 用户新需求）

用户要求：**曲库可搜索、有自己的书库、整合成一个娱乐系统、再扩一些小游戏（最简是旅行青蛙，让澜自己去冒险）**。

这一层在原有「读书 + 唱歌」之上，所以先做完地基再谈入口。

### 7.1 已完成

| 项 | 实现 | 状态 |
|---|---|---|
| 曲库 + 搜索 | `lib/song-library.js`（原曲 + 翻唱统一，`search()`） | ✅ |
| 书库 | `lib/book-library.js`（每本 `books/<id>.json`，索引 + `search()`） | ✅ |
| 书库切换/删除 | `command({action:'open-book' / 'remove-book'})`，删在读的书会被拦 | ✅ |
| 书架 UI | `#book-shelf` 横向胶囊，两本以上才出现，在读高亮 | ✅ |
| 旅行青蛙（最小闭环） | `lib/journey.js`：按真实时间补算出门、带回明信片 + 见闻、落盘成旅行日记；`#journey-panel` 折叠展示 | ✅ |
| 入口整合（第一步） | `singing` tab 改名「娱乐」（曲库 + 翻唱 + 旅行），旅行从读书页移过来 | ✅ |

**兼容策略**：`reading.json` 继续表示「当前打开哪一本」，书库只是多存一份。
旧用户不需要迁移，导入新书时自动进书库。

### 7.2 还没做

**娱乐入口整合（第二步）**。第一步已把 `singing` 改名「娱乐」并把旅行挪过来
（旅行和读书无关，放读书页是错位的）。再往下做的话：

- 顶层收敛到 **聊天 / 娱乐** 两个 tab，娱乐内部再分 曲库 / 书库 / 游戏。
- 理由：用户心智里「听歌、读书、玩」是同一类事（打发时间），而聊天是另一类（交流）。
- 但这一步会把三个面板塞进一个容器，需要重排布局，改动比第一步大得多，
  建议先看第一步的实际观感再决定。

**小游戏：旅行青蛙（澜的冒险）✅ 已落地 2026-10-31**

这个需求最有意思的地方是：它把澜从「被动响应」变成「有自己的行程」。

实现要点（`lib/journey.js`）：

- **时间用补算，不是真的等**：存 `lastTripAt`，`tick()` 时算时间差。
  app 关着 8 小时再打开，会一次性补出这几趟，而不是从打开那一刻重新计时。
- **补算上限 3 趟**：久未打开时不会一次刷出十几条。
- **时间推进到最新而不是 +count**：否则错过太多趟会反复补同样那些。
- **见闻落盘**：这是整个功能的意义所在 —— 每次新生成就攒不下任何东西，
  用户也不会觉得「她真的出去过」。日记上限 60 条，新的排最前。
- **模型挂了退模板**：8 个本地地点文案兜底，旅行不该因为模型不可用就停摆。
- **明信片复用相册图**，但**不占剧情相册的解锁位** —— 那是她带回来的新照片。
- 主进程每 10 分钟对一次账，启动时立刻补一次，不等第一个 10 分钟。

明确不做：路线选择、道具、体力值。那是养成游戏，不是这个产品的调性。

### 7.3 与已完成部分的关系

曲库和书库是**内容层**，旅行青蛙是**行为层**。
前者解决「有什么可看可听」，后者解决「她自己会做什么」。
两者不冲突，但旅行青蛙会用到书库/曲库的数据（比如「她带回来一首歌」），
所以先做完前两层再接，顺序是对的。
