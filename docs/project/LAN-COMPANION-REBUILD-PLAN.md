## 1. 产品命题与非目标

澜有自己的小屋、兴趣、行动与底线。用户可协商、帮助她读书/修炼/写作，不能用点击数控制她的性格和命运；她可以邀请、不同意、暂缓，也会接受拒绝。区别助理 AI 的不是“随机说俏皮话”，而是**能解释她为何这样做、保有经过验证的共同经历、在两个空间继续同一段关系**。

**核心价值一句话（2026-11-01 评审共识）：“下次见面，我们能接着上次一起做的事。”** 长期吸引力来自接续感——共同读到的位置、写到一半的章节、留在小屋里的痕迹都不断线；设定丰富度本身不构成吸引力，以实际体验验证为准。

两条贯穿全部切片的设计原则（2026-11-01 GPT 评审并入）：

- **自主性通过行动表现，不靠对白宣称。** 她会自己选一本书、暂缓修炼、惦记没写完的章节，并能解释原因（引用事件来源）；只在对白里说“我有自己的想法”不算达标。验收时看可观察的行为差异，不看人设文本。
- **确认流程分级、保持轻巧。** 日常走动、休息、表达偏好自然发生，不弹确认；只有作品定稿、重要剧情、持久世界改动和对外动作才需要确认＋撤销。把相处做成连续审批即为设计失败。

首版纵向价值：①一本本地书能导入、听完一段、暂停续读并围绕真实文本讨论；②澜在她的世界和用户桌面之间来去，共享一份身份与进度；③一次她主动提出、用户可以拒绝或共同完成的修仙故事，结果可回看、更正、撤销。唱歌、视频相册和工作协助保留，但不挤掉上述闭环的验收。

不做：一键“强制修炼/强制躺平”、签到惩罚、排他依恋、无边界 LLM 执行、任意长篇无限生成世界、模型逐帧控制场景、全书上传、未许可角色/声纹/翻唱公开发布、把 Vidu 实时数字人当首版依赖。

## 3. 叙事底座：固定起点，开放过程

**现行正典仅含**：澜=小肥鱼；弱小门派出身；遭强宗/天骄压制后被打回原形；与用户是异界结契的伙伴；她有自我选择。宗门名称、对手动机、具体失势原因、契约代价、原形外观、真人/Q 版转换机制、最终胜负尚未批准。旧“轮回瓶、突破失败、遭人暗害”的因果不能自动并入。

建议采用“世界规则卡 + 角色卡 + 可变状态 + 已发生事件 + 创作草稿”的五层结构：

1. 世界规则卡：不可自行违反的修仙资源、境界与契约限制，允许版本修订并记录迁移。**内容由设计稿和用户审核进入**，不是由模型即兴改规则。
2. 角色卡：澜不服输，也会疲惫、好奇、爱读书；是初稿提案，不以模型输出替换稳定核心。敌方宗门做原创名与动机；“克劳德/柴德吉皮提/珍穆耐”仅作内部占位，公开前完成命名与 IP 核查。
3. 状态：当天精力、兴趣、修炼意愿、休息偏好、正在做什么、与用户约定；状态会变但没有“勤奋=好/肥鱼=坏”的道德评分，也不以点击好感直推剧情。
4. 事件：实际开始/完成/中断的活动、真实阅读位置、用户确认的作品/世界改动。事件带来源、范围和撤销/修订记录。
5. 作品：澜写的“自传体讲述”与纯小说/剧本草稿分栏，只有被确认的选择才进**作品正典**；作品正典不等于用户个人事实，也不等于澜在现实中真的经历了情节。

**双空间解释只立约束，不提前定桥段**：两形态同一个澜、同一记忆、同一阅读/作品进度；出入需同一入口控制，单舞台播音，不能让她的世界和桌面各自推进一条独立人生。提案可探索“契约投影”“两侧视角”等原创解释，先出短开篇与用户确定，之后才制作视频。真人女友式实时互动是未来第三种表现，不是新角色。

## 4. 运行设计：一个意志，多处呈现

现有 Electron 主进程保留窗口/IPC/会话所有权，不重建数据库或前端框架。在它旁边新增小模块，先纯函数和隔离数据测试，再由单一文件负责人接线。

```text
用户真实输入/读书实际位置/场景动作
        ↓ 验证和权限规则（确定性）
带来源的事件账本 ─→ 澜的状态快照 ─→ 有限行动选择器
        │                 │                    │
        │                 └──→ 世界/桌面统一呈现 ←─┘
        ├──→ 上下文编译器 ─→ 可提议的故事导演（LLM 写候选，不落盘为事实）
        └──→ 经确认的作品正典/场景改动/可纠正个人记忆
```

### 4.1 状态决定与冷却规则

- **优先级排序**：安全/免打扰 > 用户明确约定 > 休息与资源 > 当前兴趣 > 邀请共读/共创。一次只能有一个活动；聊天、读书、唱歌或 agent 任务占用时不抢播放。
- **状态数值与枚举**：快照包含精力（`energy: 0..100`）、当前心境（`mood: focused | idle | tired | inspired`）、当前活动（`activeTask`）及动作冷却表（`cooldowns: { [actionType]: ISO8601_unlock_time }`）。
- **低频 Tick 与离线结算**：前台低频 tick（默认每 5~15 分钟评估一次）只作确定性规则选择，LLM 仅在有具体故事提案/对话时调用。后台/关机重启时的时间差只用于恢复精力或推进纯单人独处状态（如 `status: simulated` 的“独自看完了半卷闲书”），**绝不编造和用户共同发生的事，也不生成阻塞式待审批弹窗**。
- **拒绝冷却硬约束**：用户拒绝或忽略某类轻确认邀请（如 `invite.co_read`、`invite.co_write`）后，该动作类型立即写入冷却期（默认 4 小时或当前会话内不再主动发起），不掉好感，不进行二次挽留轰炸。允许澜基于自己目标提出异议，但持久世界改动、文件/网络动作和对外发布始终由用户授权。

### 4.2 确认分级与桌面非侵入交互

1. **免确认**：独处活动、走动、休息、阅读位置记录、临时偏好表达。
2. **轻确认**：她提出的邀请/故事方向，用户选/改/拒一次即可，不做多步审批。
   - **桌面模式（Pet）非侵入约束**：当处于透明桌面窗口且产生轻确认提案时，**严禁弹出模态框或抢夺系统焦点（No Focus Stealing）**。仅在角色旁浮现非模态微气泡/状态图标，保持透明区域鼠标穿透（`setIgnoreMouseEvents(true, { forward: true })`）。若用户 3 分钟内未点击交互，气泡自动安静收起，该提案自动转为澜的“独处备忘/草稿想法”，留待下次用户主动打开面板时再自然提起。
   - **免打扰感知**：当用户开启免打扰、麦克风被会议占用或处于全屏独占应用时，自动挂起主动语音与轻确认气泡，保持安静陪伴。
3. **强确认**：作品进正典、小屋持久改动、文件写入、对外发布，必须确认＋可撤销＋留收据。级别只升不降：低级别产生的输出不得伪装成高级别结果。

### 4.3 状态接口、事件契约与软失效（Tombstone）边界

- **核心接口提议（非现有 API）**：
  - `getSnapshot()`：返回 `characterId=lan`、当前空间/活动、活跃目标、状态枚举、可解释原因及引用的有效 `eventIds`。
  - `propose(action, context)`：只返回符合白名单 Schema 的候选提案（`status="proposal"`），不落盘为事实。
  - `apply(approvedAction)`：验证前置条件、幂等 ID 后追加事件并产出新快照。
  - `undo(eventId)`：追加补偿事件（`type="event.retracted"`），不静默抹掉历史日志。
  - **LLM 边界**：不直接让 LLM 任意调用 shell、修改 pack、访问真实用户目录；先按 P1-0 冻结契约并经 Mock 验证，再定 IPC 名称。
- **事件样例（设计契约，不是当前文件格式）**：

```json
{"id":"evt-1","schemaVersion":1,"type":"reading.segment_finished","actor":"lan","occurredAt":"<ISO8601>","source":{"kind":"reader","bookId":"book-1","segmentId":"seg-1"},"scope":"shared","status":"observed","invalidatedBy":null}
```

- **事实与迁移纪律**：`occurredAt` 只记录实际观察到的完成时间；`source.kind=simulated` 的离线故事不可参与现实关系或成果统计；模型建议在未获用户确认前仅作为 `proposal`，不得宣称共同经历。既有 `memory.jsonl` 的 `{t,u,a}` 先保持兼容，新事件用独立版本文件，不在旧聊天行上伪造来源。写入用原子快照/追加幂等收据，重启重放可重建；定义数据保留、删除/导出时的派生摘要处理，再接真实用户数据；先隔离目录迁移演练、备份并验收，再考虑真实数据迁移。
- **`undo` 级联与软失效边界**：首版仅要求对**最近确认的正典节点**或**独立挂载物（如小屋纪念物摆放、单章正典入库）**支持一键撤销。当 `evt-x` 被 `undo` 时，系统将其标记为 `invalidatedBy: "evt-undo-x"`，并自动将依赖 `evt-x` 的衍生品（如关联摆放的纪念物收回、关联记忆摘要标为失效）一并软失效，无需复杂的全图历史重算。

### 4.4 上下文编译器（Context Assembler）与输出校验

为防止不同模块拼装 Prompt 时混入虚假记忆或导致 Token 爆炸，所有调用 LLM（对话或故事导演）的入口必须经过统一的纯函数上下文编译器：

1. **System 层（只读契约）**：注入世界规则卡摘要 + 角色卡核心设定。
2. **State 层（真实快照）**：注入 `getSnapshot()` 当前状态，以及最近 $N$ 条满足 `status === "observed" && !invalidatedBy` 的共同事件；**硬性过滤掉 `simulated`（模拟推演）、未确认的 `proposal` 以及已被 `undo` 软失效的记录**。
3. **Workspace 层（按需局部注入）**：仅在共读时注入当前 `bookId/segmentId` 附近的真实原文片段；仅在共创时注入当前正在讨论的草稿段落與最新作品正典大纲。
4. **结构化输出与引用校验**：故事导演返回必须符合固定结构（含 `dialogue`、`proposedOptions`、`referencedEventIds`）。代码层在展示前必须校验 `referencedEventIds` 均存在于真实账本中且未失效；若模型凭空捏造不存在的事件引用或违背世界规则卡，自动拦截并降级为静态安全对白。

### 4.5 跨窗口视图与媒体仲裁协议（View & Media Lease）

- **视图无状态化（Dumb Views）**：`world.html`（小屋）和桌面宠物渲染进程只负责表现与输入转发，**严禁在渲染层各自维护独立的活动计时器或剧情推进状态**。
- **切换世代号（Generation Token）**：主进程维护单调递增的 `viewGenerationId`（现有代码的 `AUDIO_EPOCH` 即同型实践，接线时统一命名对齐）。每次发生“小屋 ↔ 桌面”空间切换或形态切换时，`viewGenerationId` 加 1；任何携带旧 `viewGenerationId` 的异步 LLM 响应、动画回调或延迟 IPC 消息在到达时一律丢弃，杜绝切形态时的状态闪回。
- **单一音频租约（Audio Lease）与抢占**：全局仅允许一个音频通道持有播放权，优先级固定为：`用户语音唤醒/打断 > 实时对话语音回复 > 共读电子书朗读 (TTS) > 唱歌/环境动效音`。当高优先级音源抢占或发生空间切换时，共读 TTS 执行 `pauseAndSaveOffset(bookId, segmentId, charOffset)`，待高优先级结束或新窗口就绪后，从断点无缝续播，绝不出现双窗口重音或进度丢失。

### 4.6 内容与玩法接口

旧 `pack.json` 的 album/chapters/songs IDs 和奖励不原地改义。新修仙故事底子为独立带版本内容包；世界规则/人物/剧情节点/素材引用均有 ID 与来源。首片只做“被打回原形→她主动提出结契或暂缓→小屋里的第一项自选活动”；结契不赋予用户强制训练权。故事导演给两个合理提案，筛去违反正典/无法用现有资源演出的提案，未通过则静态安全支线；作品草稿、确认正典、已呈现剧情状态分开存。单一章节图文/现有视频可先作演出容器，真人视频不必实时生成。

**检查点**：P0 未通过，P1 可做纯模块和内容草案，但不向用户宣称“真能读/双空间稳定”。P1-0 契约未冻结前，各业务分支不得擅自向 `main.js` 塞私有 IPC。P1-1/P1-2 通过后先在当前舞台试玩“她自选活动、用户拒绝也不停摆”；合格小屋接入后再验房间内可见动作。P1-3/P1-4 通过后试玩一次“共同写作→留下纪念物→重启→撤销/导出”。任何失败回退到当前稳定版，不删唯一可用包；已有数据迁移先备份→替换→读回核对。

**首个整合试玩 PILOT-REUNION-01（2026-11-01 GPT 评审并入；跨重启接续小体验）**：把 P0-1、P1-3、P1-4 串成一条用户可完整走完的链路——**一起读一段书（真实朗读、暂停续读）→ 她主动提出一个与自身处境有关的想法（引用书中位置）→ 用户选/改/拒，同意则共同写一小段进草稿 → 定稿后在（届时已接入的）小屋留下一件纪念物 → 重启 App、切换形态后，从读到的那页、写到的那段、留下的那件东西准确接续**。它不是新切片，而是上述切片的整合验收场：任何一环断链即整个试玩不通过。小屋届时未接入则纪念物环节降级为“小屋预览页可见”，不得冒称已接 Electron。该试玩是三板块架构下板块①的第一个端到端里程碑。

## 6. 多 agent 分工与交接纪律

- **叙事/内容负责人**：独占新修仙世界规则卡、原创宗门人物卡和首章内容包。只写新文件，不改旧 `pack.json`；严格遵守 P1-0 冻结的 `ContentPack` Schema；输出来源、用户已定/作者提案两栏和内容审核清单。
- **状态/记忆负责人**：独占 `lib/lan-*` 新事件/状态/上下文编译器模块与测试，明确版本、存储、迁移、`undo` 软失效与数据删除；先不碰真实个人目录。与旧 `memory-store.js` 的兼容通过适配层，不重写既有历史。
- **场景/视觉负责人**：独占 `web/moli-room/` 与角色资产的演出适配；先确认授权及用户认可的澜形象。失去 GLB 导出权时不伪称已接入；渲染层保持无状态（Dumb View），与 Electron 接口先用 P1-0 的 Mock 数据验契约。
- **阅读/声音负责人**：继续 DW-05 实书试听、TTS 断点保存（`pauseAndSaveOffset`）/播放租约仲裁与 WAKE-01 实测；不让新剧情接入修改其正在工作的媒体模块。
- **集成负责人**：单独持有 `main.js`/`preload.js`/`world.html` 的接线窗口；依据 P1-0 冻结契约处理 `viewGenerationId` 异步晚到丢弃、换形态、音频单播租约、桌面穿透权限、IPC 白名单；与 WorkBuddy/既有负责人明确交棒，不能见文件已修改就自行覆盖。
- **测试/许可负责人**：隔离目录回归、Schema 契约自动化校验、打包证据、素材授权及非商业发布审计；不直接写业务文件。

每个任务：在 TASKS 登记负责人/文件范围/完成条件；保存本任务 updates 交付与基线证据；更新 STATUS 与 CHANGELOG。交付口径分为“代码存在→包内一致→入口可用→真实服务实测→视觉/听感验收”。`bash scripts/project.sh check` 只代表静态规则，不等于 App 功能验收。并行修改期间先核当前 mtime/内容，不对热文件构建半成品。

## 7. 回归与失败场景

- 故事一致性：模型凭空宣布境界提升、改写世界规则、让失败敌人复活、捏造不存在的 `referencedEventIds` 或把草稿当正典 → 上下文编译器与输出校验层直接拦截，阻止自动持久化，展示候选/原因，回退安全支线。
- 关系边界与桌面打扰：用户拒绝、忽略气泡、数日未开 App、模型网络掉线 → 触发动作冷却，不降好感、不催回复、不抢系统焦点、不编“我昨晚一直等你”；澜有低风险独处状态，但不补造共同事件。
- 数据与撤销：断电中断写入、重复 IPC、切形态时旧 `viewGenerationId` 异步返回、`undo` 撤销或删除后旧摘要再次进入 Prompt → 原子写/幂等、世代号丢弃、软失效（`invalidatedBy`）过滤、导出与删除读回验证。
- 体验与媒体抢占：读书/唱歌/聊天争音频，隐藏窗口持续采麦，桌面层挡鼠标，场景切换视频卡死 → 遵守单一 Audio Lease 优先级与断点续播、权限开关与明显状态、真实 Electron 操作验收；不以脚本模拟代替。
- 授权：代码 MIT 不等于素材可用；moli-room CC BY-NC 不等于后续可商用；示例 Live2D、同人小游戏、真实人声和现成歌曲分别列公开包排除/授权状态。

## 8. 需要用户确认的创作题，不阻塞 P0

1. 被打回原形的视觉是小鲸鱼、鱼形/半人形，还是先沿用现有 Q 版作为暂代？新设定不自动授权重做已否定的 3D 拼接角色。
2. 首章对手的原创名字、动机，以及结契的代价；真实世界与桌面切换如何表现。先出两三句开篇提案，再由用户选；不能沿用轮回瓶镜头。
3. 澜“写自己的故事”与玩家写小说的默认界面，是两套作品库还是同库分作者；实现前必须确认作品正典的批准者和公开版权归属。

这些未决项不能被 agent 擅自补成“已批准”；P0 基线核验、P1-0 契约冻结与 P1-1 纯事件协议可先行。
