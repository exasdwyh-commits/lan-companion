# COVER-FIX-01：翻唱不执行/反复失败

日期：2026-10-31。负责人：Codex / BMAD 安装与修复聊天；用户本轮指定接手翻唱故障。

## 已确认的原因

1. `sing_cover_file.sh` 的时长探测用 `ffmpeg -i` 接 `grep/sed/awk`。`ffmpeg -i` 无输出参数会在输出元数据后退出 1；脚本 `set -euo pipefail` 把它当作整条流程失败，停在人声分离之后。macOS 上原有 sed 替换表达式还缺结尾 `/`，实际报语法错误。
2. 完成混音后再次用同样的 ffmpeg 探测管线，可能已有成品却以失败退出；上层只认退出码，不登记曲库。
3. 分片拼接清单把 `$PWD/` 加到绝对 WORK 路径前；含单引号的路径在原有 Python 插值、ffconcat 中也不能安全处理。
4. `split_vocals.plan_bounds()` 为尾部保留 min_gap，会放过 30～34 秒整段；迭代又写死 CHUNK，非默认上限不生效。这违背已有“每段 <30 秒避免长曲 OOM”的契约。这里只确认越界，不把每次用户失败都归因于 OOM。
5. `cover-jobs.js` 丢弃全部 stderr，只返回通用“制作失败”，没有阶段与分片进度，用户难以区分没有启动、正在推理和已经失败。

只读查看此前失败任务的中间产物：最近两个失败任务都有参考、归一化文件和两条分离轨，没有 chunk-plan 或换音色产物，与探测处中断吻合。未输出原曲内容、个人设置或聊天/画像。原生客户端实际观察到：已选原曲、制作按钮可点、下方显示通用失败提示；这本身不证明按钮点击后的完整链路。

## 修改

- 时长用所选 sing Python 调用 ffmpeg 后解析元数据，单独处理其预期退出码；移除坏 sed 和 pipefail 误判。
- Python 参数通过 argv 传入；拼接使用真实绝对路径并按 ffconcat 规则转义单引号。
- 分片循环依据剩余时长和传入 chunk，确保每段严格服从上限，包括临近末尾的片段。
- 混音先输出临时 m4a，完整解码通过后再替换成品。
- 子进程只向上层暴露固定阶段名、退出码与数字分片进度；不保留原始 stderr。面板增加 renderCover 的进度文字，并把长曲耗时提示改为“可能需要数十分钟”；保留并行 agent 新增布局、曲库和读书实现。
- 沿用既有模型/参考音色、studio 整形、30 步推理、取消进程组与缓存续跑，不以 TTS 假装翻唱。

## 收尾证据与限制

- `real-result-first.json`：第一次 GPU 运行在 10 段转换完成后退出 127。运行期间曾修改正在执行的 shell 脚本，可能影响后续脚本读取，但未保留原始 stderr，不能断言该退出的具体命令。当前脚本的长分片路径已另有真实 ffmpeg 回归；本任务又复用 10 个真实片段重新执行长分片循环、拼接与整形，不能把首轮失败抹成一次成功。
- `real-result.json`、`real-audio-verification.json`：最终隔离控制器完成状态与整首解码；`native-verification.json`：原生短曲制作和播放状态、成品解码；`packaged-verification.json`、`build-final.log`：最终包校验。
- 原生验收明确创建了一首 tide 测试翻唱并写入本机曲库（与聊天/记忆无关）；之前失败的原始任务与原曲未修改。隔离长曲产物没有自动加入个人曲库。
- 收尾时界面又出现一首原曲的新任务，已显示“第 1 / 10 段”。保留该正在运行的任务，不再退出/重启客户端，未把它标成已完成。
- 原生播放确认到 UI 的播放状态与音频解码；本轮没有人耳评价音色、接缝或整首听感。
