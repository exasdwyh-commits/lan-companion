# DESKTOP-SELF-01 · 桌面形态的自我定位与走动

> 2026-11-01 22:05 · WorkBuddy / 本聊天
> 用户报告：「桌面模式，目前 ai 不能识别自己在哪，我让她去左边，自己被遮挡了它不知道，看来它只能对话」

---

## 一、根因：不是模型笨，是提示词里根本没有位置

桌面形态的舞台窗口是 `type: "desktop"` —— **壁纸层**。任何普通应用窗口都盖在她上面。
渲染层（`world.html`）知道 `pet.x/pet.y`、知道屏幕上有哪些窗口（`wins`）、甚至知道她挂在哪个窗口的顶边（`perch`）。

**但拼 system prompt 的是主进程，而主进程对她位置一无所知。**

于是「让她去左边」这件事，她的上下文里只有一个意思：一句普通的话。
走过去、被浏览器盖住、自己看不见自己 —— 她当然不知道，因为**提示词里没有任何一个字描述她在哪**。

这不是「只能对话」，是「对话时她是瞎的」。

---

## 二、三层改动

```
world.html  ──每 1.2s──▶  character:presence  ──▶  main.js
 (她知道位置)                 {x,y,w,h,sw,sh,perch,wins}      │
                                                              ├─▶ lib/presence.js（纯函数）
                                                              │     身体矩形 / 遮挡占比 / 方位 / 措辞
                                                              ▼
                                                    【你此刻在哪】进 system prompt
                                                              │
模型回复里的 [move:left] ──▶ main.js 剥标签 ──▶ character:move ──▶ world.html moveTo()
```

### 1. 渲染层上报（`web/live2d/world.html`）

`reportPresence()` 在桌面形态的每帧里按 1.2s 节流上报：

```js
{ x, y, w, h, sw, sh, state, perch, wins: [{app,x,y,w,h}] }
```

- `x/y` 是**脚底**（`pet.y` 本来就是脚底：站着时 `H-2`，站在窗口顶边时是窗口的 `y`）
- `sw/sh` 用 **`W`/`H`（窗口内尺寸）而不是 `screen.width`** —— `pet.x` 是窗口内坐标，
  两者在主屏铺满时相等，不相等时必须用前者才算得对（headless 里就撞到过：`screen` 报 1512，窗口是 1440）

### 2. 主进程推断（`lib/presence.js`，新，纯函数）

不读文件、不碰 Electron，所以能直接 `node --test`（12 条断言）。

- `bodyRect()` 把脚底锚点换成矩形；`occluders()` 算每个窗口盖住她多少面积
- 只按面积判，**不看 z 序**：壁纸层之下的舞台，任何普通窗口都在她上面，「有重叠 = 被挡」成立
- 同一 app 多窗口合并，只报最大的占比
- 阈值 `≥0.8` 看不见 / `≥0.2` 部分遮挡

产出（真实输出）：

```
【你此刻在哪】
- 屏幕 1440×900，你在屏幕左侧偏下（脚底 x≈350, y≈880），在「Code」窗口附近。
- 「Code」把你挡住了大约 100%，用户现在基本看不见你。
```

### 3. 提示词与走动

- `lib/identity.js` 的 `buildSystemPrompt` 增加**可选** `place` 参数，插在「此刻」之后、记忆之前。
  不传时输出**逐字节不变**（和 `soul` 一样的规矩）。
- `main.js` 的 `chatMessages` 在 `currentMode === "desktop"` 时追加 `DESKTOP_MOVE_HINT`，
  告诉她在回复末尾可以写 `[move:left|right|center|floor]`。
- `lib/reply-tags.js`（新）：`[emo:x]` 与 `[move:x]` 的解析和剥离**同源**。
  剥离必须彻底 —— 漏一个，TTS 会把「往左」当台词念出来。
- `moveTo()` 落点选择：**先躲遮挡，再贴方向**。

## 三、五个坑（都是实测撞出来的）

### 1. `motion.action` 会把一次 moveTo 完全吃掉

`updatePet` 里有个 `held` 判定：正在做伸展/挥手动作、鼠标停在她身上、输入框聚焦时，
她会「先站住」。实测 `moveTo({side:'right'})` 之后 **16 秒一动不动**，
`moveTarget` 一直挂着、`pet.state` 反复在 walk/idle 之间弹 —— 因为 `held` 每帧先把她按回 idle 再 return。

改法：`if (held && !moveTarget && ...)`。**被明确叫去某处时，环境手势不该压过指令。**

### 2. 落点只在前三分之一找 → 浏览器铺满左半屏时照样往里钻

第一版 `freeSpot(from,to)` 只在目标区间里扫。实测 Safari 占 `x 0..700` 时，
`moveTo({side:'left'})` 给出 `target=107` —— 完全在窗口底下，等于白走。

改成全屏候选 49 个点，评分 = `遮挡占比 + 偏离目标区间 × 0.35`：
「完全被挡」永远输给「没被挡但偏一点」，于是**能走多左就走多左，但不走进窗口底下**。
实测同一场景 `target` 从 107 变成 810，`clearOfWindow: true`。

### 3. `perch` 不说明是顶边还是底边

现有 `perchLine()` 在顶边放不下时会退回**底边**（`w.y + w.h`）——
那一刻她整个人落在窗口矩形**里面**，用户根本看不见她。
第一版照抄字段写成「站在「Code」窗口的顶边上」，紧接着又说「被挡住 100%」，自相矛盾。

改成按坐标判：`|y - w.y| ≤ 6` 才是顶边，`|y - (w.y+w.h)| ≤ 6` 是「贴在窗口下沿，人在窗口里面」。
这条同时**顺手暴露了一个老 bug**：perch 到底边时她其实是隐形的，而以前没人知道。

### 4. 「中间中部」

`horizontalOf` 返回「中间」、`verticalOf` 返回「中部」，拼起来就是「你在屏幕中间中部」。
改成 `wherePhrase()`：纵向正好在中间时不带后缀 → 「屏幕中间」「屏幕左侧偏下」。

### 5. 关掉闲逛之后她就完全不听话了

`if (!roaming && ...) return;` 把她锁死。但「被点名去某处」不是闲逛。
改成 `!roaming && !moveTarget` 才早退。实测 `roaming=false` 时仍能从 x=117 走到 962。

## 五、尚未验证 / 已知边界

- **真机听感与画面未验**：屏幕会话锁屏，截屏与 `capturePage` 都拿不到画面。
  上面所有判定来自 headless + 假宿主。**「她真的会按 [move:left] 走」这一步没在真模型上跑过** ——
  需要用户说一句「去左边」，看她有没有加标签、有没有走过去。
- **模型可能不加标签**：提示词里写了协议，但 DeepSeek 会不会稳定遵守没有实测。
  如果不加，现象就是「她嘴上答应了但没动」——那时需要退回到主进程关键词兜底。
- **多显示器**：`bounds()` 用的是主屏，`CGWindowList` 的坐标也是主屏原点，所以只有主屏是对的。
  她在副屏上的位置会被算错。
- **遮挡只看矩形**：圆角窗口、被别的窗口再盖一层的窗口，都按满矩形算。
- **`[move:floor]` 只下到地面不横移**（保持 x），避免「下来」变成「跑到别处」。
