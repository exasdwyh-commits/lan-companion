# 连续语音与预生成互动方案

日期：2026-10-31。负责人：Codex / BMAD 安装与修复聊天。

## 决定与当前边界

依据用户最新补充：常见互动语音可提前生成，期望像智能音箱一样顺畅互动。推荐先采用**本地预生成互动 + 实时开放聊天**，保留澜的 world / desktop 双音色。此处借用交互目标，不推断任何智能音箱厂商的内部实现。

本轮仅完成源码核查和可执行方案；**尚未生成互动音频、未接入播放、未实现连续语音**。不把方案中的延迟目标当成本机实测。

## 源码确认

- `web/live2d/composer.js`：固定录音 4 秒，识别后放入草稿，用户确认发送。
- `main.js:recordAndTranscribe()` 与 `stt_server.py`：录成文件后一次性 POST 转写；服务中的 `vad_filter=True` 只是这次转写的音频过滤，并非持续监听和回合结束判断。
- 聊天模型请求设置 `stream:false`；回复文字完整返回后再合成整段音频。
- `main.js:cancelChat()` 已有模型请求取消、音频 epoch 与停止舞台播音，可作为打断基础；TTS 推理本身的取消还需适配。
- `world.html:poke()` 调 `touchLine(kind)` 后只显示气泡；`lib/content-pages.js:nextLine()` 负责轮换文本，没有固定互动语音播放。
- `lib/audio-cache.js` 已由读书使用；其现有调用不代表固定互动音频已缓存。

## 分三条路径

| 输入/事件 | 处理路径 | 完成条件 |
|---|---|---|
| 点击、趴屏互动、唤醒、固定陪伴 | 根据事件和状态选台词，直接播放本地音频 | 不请求聊天模型，不现场调用 TTS |
| 明确的播放/暂停/继续等命令 | 本地意图匹配 → 执行动作 → 按真实结果播放固定回应 | “已暂停”等成功台词只在动作成功后播放；不靠模糊关键词触发有副作用操作 |
| 开放闲聊 | 识别 → 流式模型 → 按句 TTS → 舞台顺序播放 | 可连续接话、可打断；临时应答不能冒充正式答案 |

预生成只去掉固定输出的模型/TTS等待，**不能取代语音识别、自动判断停顿或回声消除**。预制一句“我在”也不能证明用户已经被正确识别。

## 资产和运行契约

- 新产物保存到 `assets/` 的独立互动语音目录，保留源文本、生成参数、引擎/模型版本、音色描述与文件校验值。源码及素材许可分开登记，不直接修改 dist。
- 每个条目标明 `event / variant / mode / text / textHash / voiceFingerprint / file / duration / sha256`。同一条显示文字与播放音频绑定，不拼接可能读错的人名。
- key 包括文本、实际音色描述、引擎/模型版本与处理版本；不只用 world/desktop 名字作缓存键。切形态或换音色后不能误用旧音轨。
- 预生成是独立、可续跑的构建前任务；默认启动不批量生成，不挤占聊天的合成队列。失败文件可重试，不能只凭 HTTP 200 计作成品；需解码、检查时长与音量并试听。
- 运行时先查包内音频，再按明确策略降级为文字或按需合成；失效/缺文件要有诊断，不能声称“本地命中”。
- 复用现有舞台音频调度，保持一个播放主体。频繁触摸合并/冷却、不无限排队；普通触摸不能打断读书、唱歌和正式聊天。被用户主动打断后清空旧队列，晚到音频不恢复播放。
- 动作确认语音可高优先级；问候与等待短句低优先级。正式回复就绪后丢弃未播的等待句，不每轮机械说“稍等”。

## 实施顺序与文件归属

1. **固定互动语音包**：新生成器、新 manifest、资产来源记录与独立加载模块；验证 16 条双音色，接现有 `touchLine` 事件和舞台播放。缓存热命中不得调用模型/TTS。
2. **本地控制与连续接话**：明确开启/结束语音模式，持续麦克风采集、回声消除、语音活动检测、结束说话自动提交；保留草稿确认模式作选择。先把“停止/暂停/继续”的动作与结果反馈做可靠。
3. **开放聊天提速**：流式模型按句输出、受限长度的 TTS 队列、交互优先于读书预取。打断要同时停止播放、清队列、取消旧模型与可取消的合成；不能将未播完内容当作用户已听完。

当前 main/preload、composer、媒体与播放链由 DW-03/04/05 多项任务涉及，**此方案不领取这些共享文件的写入权**。实际接线需先在 TASKS 明确单一集成负责人；生成器、独立语音包与加载模块可以单独划定范围，不另建播放器或平行工程。

## 验收

- 16 条源素材存在、可解码、有 manifest、可追溯来源；两形态音色分别试听。
- 触摸、唤醒、趴屏：文字与声音一致；断网且关闭模型/TTS服务时仍可播预制语音。按测试环境执行，不终止用户现有服务。
- 热命中统计模型调用 0、TTS调用 0；分别记录事件到首个可听音频、停顿到首音、插话到静音的 p50/p95，不用文件加载完成替代实际可听延迟。
- 多次点击、聊天中点击、读书/唱歌中点击、切形态、停止后晚到音频、缺素材、权限拒绝和窗口关闭均不叠播、不恢复旧回答。
- 连续聊至少 10 轮；扬声器外放与耳机分开测，确认她不接自己的话。断网/识别失败可恢复，退出语音模式确实释放麦克风。
- 最后统一构建、源包比对、签名检查及真实原生试听；逻辑替身测试不算完整听感验收。

规划核查记录见 [VOICE-PLAN-01](updates/2026-10-31-VOICE-PLAN-01-hybrid.md)。

# 实时语音对话改造（VOICE-PLAN-02）

日期：2026-10-31。本文是上一节的**深化与修订**，不是第二份方案：上一节回答「分哪三条路径」，本节回答「实时那条路具体怎么改、卡在哪、先做什么」。

用户判断：实时对话优先于其他功能扩展。此判断成立——它同时解锁语音陪伴、读书交互、语音下达 agent 任务和主动搭话，是「工具→伙伴」最短的一段距离。

## 一、实测得到的三个硬约束

在动手设计前先量了现有服务，三条结论直接决定了方案形状。

| 约束 | 实测 | 证据 | 对方案的影响 |
|---|---|---|---|
| STT 耗时与音频长度**几乎无关** | 1.5s / 3s / 8s 音频分别 0.86 / 0.81 / 0.86 秒 | `POST 127.0.0.1:8090/stt` 各跑 2 次 | **不要优化 STT**。0.8s 是固定开销（模型调用 + `vad_filter`），已达可接受区间 |
| STT **不能并发** | 单请求 0.82s；两请求并发 → 1.43s / 1.62s | 同时发两个 8s 请求 | faster-whisper 单实例串行。**放弃「边听边增量转写」**，只能端点后整段提交 |
| TTS **只有阻塞式接口** | 仅 `POST /tts` 返回完整 wav；`ThreadingHTTPServer` + 模块级 `_SYNTH_LOCK` | `~/.smartcompanion/tts_server.py:69,159` | 无流式音频可用。只能靠「首句切短」+「播第一句时合成第二句」 |

测量边界：用的是 `assets/whale-video-test/voice/ref-vivian.wav`（演唱参考人声）裁段，不是真实口语；数值是**指示性**的，不是对话场景基准。绝对耗时随机器负载浮动。

**结论重排**：真正的浪费不是 STT，而是「固定 4 秒窗口空等」+「LLM 等整段」+「TTS 等整段」。这三段是串行等待，不是算力不足。

## 二、延迟预算（首音 = 你停止说话 → 听到第一个音节）

| 段 | 现在 | 目标 | 依据 |
|---|---|---|---|
| 端点判定 | 固定录满 4.0s | 0.4–0.6s（尾静音阈值） | 静音 450ms 判定收尾 |
| STT | 0.8s | 0.8s | 实测，暂不可压 |
| LLM | 3.5s（等整段） | 0.7–1.2s（首句到即返回） | 流式首句 |
| TTS | 2.0s（等整段） | 0.8–1.2s（首句 8–15 字） | 单条 2s 是整段；短句显著更快 |
| **合计** | **约 10.3s** | **2.7–3.6s** | 保守估计，以实测为准 |

比起「首音 2 秒」的激进目标，这个数字更接近能兑现的。但体验上的差别不在 10s→3s，而在**从「流程」变成「来回」**：后面的句子边播边合成，你可以在她说完前插话。

## 三、V1：半双工流水线（不依赖回声消除）

> **已实施（2026-10-31）**，见 [VOICE-02 交付](updates/2026-10-31-VOICE-02-capture.md)。与下方设计有三处偏差，均已按实测修正：
> ①IPC 不是 `voice:start/stop/utterance`——渲染进程自己起停，主进程只保留 `companion:transcribe` 与 `voice:activity`；
> ②采集用 `AnalyserNode` 轮询而非 AudioWorklet，录音交给 `MediaRecorder`，省掉手写 WAV 编码；
> ③**opus 码率必须锁 64k**，默认档会把「海风很轻」转成「海峰很清」。
> 真麦克风端到端仍待现场验收。

关键取舍：**她说的时候不采集**。这是最正常的对话礼仪，也让我们在 V1 完全绕开 AEC 这个最脏的问题。

### 采集改造（这是根，不改则后面全部无效）

现状是主进程 `ffmpeg -f avfoundation`（`main.js:78-86`），这条路**永远拿不到回声消除和端点检测**。改为渲染进程 `getUserMedia`：

```js
navigator.mediaDevices.getUserMedia({
  audio: { echoCancellation: true, noiseSuppression: true,
           autoGainControl: true, channelCount: 1 }
})
```

拿 MediaStream → AudioWorklet 取 Float32 PCM → 下采样到 16k Int16 → IPC 交主进程 POST `/stt`。

不直接在渲染进程发 HTTP：保持「所有本机服务调用都在主进程」的现有契约，也避开 CSP `connect-src` 的不确定性。

### 端点检测：V1 先用 RMS，不引 ONNX

| 方案 | 依赖 | 判断 |
|---|---|---|
| AnalyserNode RMS + 自适应噪声底 | 零新增依赖 | **V1 采用**。安静房间够用 |
| Silero VAD（onnxruntime-web） | 约 2MB 模型 + 10MB+ 运行时 | 误触发率高时再上；包体敏感 |
| Smart Turn v3 | 8MB 量化 ONNX | 留给 V2 判「语义说完」，V1 不做 |

规则：连续语音 > 300ms 起录；尾部静音 > 450ms 且累计语音 > 600ms 判定说完。已知短板：持续背景噪音（风扇、空调）会让自适应阈值漂，届时换 Silero。

### 流式对话链

新增 `lib/stream-chat.js`，职责单一：把流式 token 切成「可说出口的句子」并派发合成。

- 请求：现有 `llmOnce` 用 `execFile("curl")` 一次拿完，改成 `spawn` + `curl -N --no-buffer` 逐行读 `data:` 行，复用已有 `ChatRouter` 的源顺序与熔断。
- 切句：**直接复用 `lib/narration.js` 的 `splitSentences`**，不另写一套。
- 首句策略：第一段额外按逗号切到 ≤15 字就先合成，宁可语气碎一点也要先出声；第二句起按正常句长。
- 合成：仍走 `synthesizeVoice`，但**串行排队**（服务端有全局锁，并发只会增加排队和超时风险——这条在 DW-05 压测里已被证明）。

### 播放：加队列，改一处语义

`companion-playback.js:17-26` 现在 `load()` 先 `stop()`，任何新音频都截断旧的。新增 `enqueue()`：追加到队列尾部，当前片播完接下一片。`stop()` 语义**保持不变**（打断依旧是硬停 + 清队列），这样 `character:stop-voice` 和 `AUDIO_EPOCH` 作废机制无需改动。

### 文件归属

| 文件 | 改动 |
|---|---|
| 新增 `web/live2d/voice-capture.js` | getUserMedia、AudioWorklet、RMS 端点检测 |
| 新增 `lib/stream-chat.js` | SSE 解析、句切分、首句优先调度 |
| `web/live2d/composer.js` | 录音交互由「4 秒倒计时」改为「说完自动发」，保留手动静音键 |
| `MALFOY-ENGINE/main.js` | 新 IPC：`voice:start` / `voice:stop` / `voice:utterance`；`companion:chat` 分流式与整段两条路径 |

| 只复用不改 | `narration.js`（切句）、`voice-script.js`（分段合成范式）、`audio-cache.js` |

### 实现落点（VOICE-03，2026-10-31 已完成代码）

上面是计划，实际落地有四处不一样，都是实测后改的，交付细节见
[VOICE-03 记录](updates/2026-10-31-VOICE-03-stream.md)：

1. **没有 `lib/stream-chat.js`**：编排放在 `main.js` 的 `streamChat`（它需要 `pushToCharacter`/`AUDIO_EPOCH`/记忆，搬出去反而要开一堆回调），可单测的部分拆成两个纯模块——`lib/llm-stream.js`（SSE 解析）与 `lib/reply-splitter.js`（切句）。
2. **切句没有复用 `narration.js:splitSentences`**：那个是按书本语料写的（先按句切、过长再按逗号二级切、上限 `PARA_HARD`），而流式要的是「首块尽量短 + 后续按**播放余量**放大」，两者目标相反。硬套会让第二句必断档。
3. **块长度是解出来的**：实测**合成耗时 ≈ 0.47 × 播放时长**（12/16/22/30/46 字重复误差 <0.02s）。串行合成下不断档的条件是 `下一块 ≤ 2.1 × 已切总量 + 4 字`（4 字换 400ms 自然停顿）。早期固定 46 字，实测第二句处空 1.6s。
4. **每句改 wav 直传**：`synthesizeVoice({wav:true})` 跳过 mp3 转码。每句转码要 0.3–0.5s，而每句播放只有 2–5s，这笔开销占比太高；base64 体积约 4 倍（100KB 级），本机 IPC 无感。

另外两件计划外但必须做的事：

- **首字闸门**：流式等的是「首个正文 token」而不是整段。默认 5s——健康源实测 1.9–2.7s，网关排队能到 3.6s（2.6s 会误杀），而真卡住时观测到 38s 才出正文。出过正文就不换源。
- **模型池重排**：把「先吐 12s 思考再出正文」的 `qoder/qfmodel` 压到最后，`ollama/local27b` 从网关中间挪到末尾。原来前两个云端源一 429，就会先落到本机 7b 上。

## 四、V2：打断（这一步才真正需要 AEC）

V1 跑顺之后，打断是自然的下一个需求——不能插话的对话仍然像对讲机。

判据与技术路线，按成本从低到高：

| 路线 | 做法 | 代价 | 何时用 |
|---|---|---|---|
| A | 同一渲染进程内 `getUserMedia({echoCancellation:true})` 采集，TTS 也在同进程 `<audio>` 播放 | 零 | **先测这个** |
| B | macOS `AVAudioEngine.voiceProcessingEnabled` | 需原生模块 | A 不够用时 |
| C | GStreamer + WebRTC AEC3（Project Raven 路线） | 最重，要分发原生二进制 | 前两条都不行时 |

**必须先做的验证**：Chromium 的 AEC 参考信号来自 WebRTC 音频通道，普通 `<audio>` 元素播放的 TTS 不一定被纳入参考。这决定了 A 路线的可行性。验证方法：外放播放一条已知语音、同时用同一 `getUserMedia` 流采集，比较「她说话时」与「静音时」的采集电平差；残留回声需低于用户说话电平约 15dB 才算可用。

不要在没测这条之前写打断逻辑——否则会在「她听到自己」的假触发上反复调参。

## 五、V3：生活感

V1/V2 解决「能不能对话」，V3 解决「像不像在对话」：

- 预生成固定互动语音（VOICE-01 已在任务表，16 条 × 双音色）。
- **听的时候要有反应**：`character:activity = listening` 时驱动点头/眨眼/歪头，不能只有麦克风红点。
- **说的时候口型要跟得上**：输出侧 `analyser` 已经在 `world.html:475-484` 驱动口型，可与新播放队列对齐。
- 情绪标签→表情映射已有（`chibi-face.js`），接进流式回复即可。

## 六、明确不做

| 不做 | 原因 |
|---|---|
| 引入 Pipecat / LiveKit Agents | Python 全家桶 + 服务端模型，与 Electron 单机桌宠不匹配；只借分层思想 |
| 换 TTS 引擎换低延迟 | 音色是产品核心，Qwen3 双音色已定调并经用户认可；不为了快牺牲她是谁 |
| OpenAI Realtime / Gemini Live | 音色不是她，人格会漂，且要持续联网与费用 |
| 边听边增量转写 | STT 服务不支持并发，实测排队；收益不足以改造服务 |
| 用「嗯…让我想想」垫时长 | 上一节已明确：不每轮机械说等待句。预制语音只用于**事件**（点击/唤醒），不用于填空 |

## 七、验收指标

不用「感觉快了」验收，用这四个数：

| 指标 | 目标 | 怎么测 |
|---|---|---|
| 停止说话 → 首音 p50 / p95 | 3.6s 内 / 5s 内 | 主进程打点，记录 VAD 收尾时刻到 `play` 事件 |
| 开口 → 静音（V2） | 300ms 内 | 用户说话起点到 `audio.pause()` |
| 连续 10 轮 | 无叠播、无自激、无旧回答复播 | 外放 + 耳机各测一遍 |
| 故障降级 | 断网/服务挂仍能文字回复 | 停掉 TTS 服务后发一轮 |

延时不看「文件加载完成」，只看真实 `play`。回环测试不算听感验收。

## 八、建议顺序

1. **AEC 30 分钟验证**（第四节），结果决定 V2 走 A 还是 B/C —— 先做，因为它可能推翻 V2 设计。
2. **VOICE-02 采集与端点检测**：把 4 秒窗口换成说完自动发。哪怕 LLM/TTS 还没流式化，这一步单独就把首音从 10.3s 拉到约 6.8s。
3. **VOICE-03 流式链**：SSE + 切句 + 播放队列，拉到 3s 级。
4. **VOICE-04 打断**：按 AEC 结论落地。
5. VOICE-01 预生成语音包可与之并行，不共享 main/preload 写入权。

拆解见 TASKS 的 VOICE-02 / 03 / 04；本轮实测与设计记录见
[VOICE-PLAN-02](updates/2026-10-31-VOICE-PLAN-02-realtime.md)。
